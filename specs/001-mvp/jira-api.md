# Process X-ray: як дістати історію процесів із Jira

Версія 0.1, 22.11.2026. Дослідження, без коду. Доповнює [concept.md](concept.md) і закриває його пункти 🔸 про CORS, PKCE і ліміти.

Позначки: ✅ перевірено в офіційній документації Atlassian, 🔸 з форумів або не до кінця підтверджено, треба перевірити в спайку.

---

## 0. Коротко

- **Історія процесу в Jira є повна.** Кожна зміна статусу, виконавця, пріоритету, спринту зберігається в changelog з часом і автором. Цього достатньо для справжнього process mining: карта переходів, час у статусах, повернення, передачі між людьми.
- **Як тягнути:** JQL-пошук дає список задач (`POST /rest/api/3/search/jql`, пагінація через `nextPageToken`), а історію беремо пачками через `POST /rest/api/3/changelog/bulkfetch` або по одній задачі через `GET /rest/api/3/issue/{key}/changelog`.
- **Головне відкриття щодо «без бекенда»:** з браузера можна ходити в Jira напряму, але тільки через `api.atlassian.com` з токеном OAuth 2.0 (3LO) ✅. CORS там дозволений. Проблема лише в одному кроці: обмін коду авторизації на токен вимагає `client_secret`, а PKCE Atlassian досі не підтримує ✅. Отже потрібна **одна крихітна безстанова функція** (serverless, ~30 рядків), яка тільки міняє код на токен. Самі задачі через неї не йдуть: браузер тягне їх напряму з Atlassian.
- **Пастка для публічного сервісу:** з 2 березня 2026 OAuth-застосунки мають ліміт **65 000 «балів» на годину на весь застосунок, спільно для всіх клієнтів** ✅, поки Atlassian не перевірить застосунок і не дасть ліміт на кожен сайт. Одна вигрузка 5 000 задач з'їдає ~10 000+ балів. Для демо це не проблема, для масового безкоштовного сервісу проблема. Запити з API-токеном (CLI, скрипт) під бальну систему **не потрапляють** ✅.
- **Рекомендація для демо:** кнопка «Підключити Jira» (OAuth 3LO) + крихітна функція обміну токена. Це найкраще виглядає на показі: натиснув, дозволив, через хвилину бачиш карту. CLI з API-токеном лишається запасним шляхом для великих вигрузок і корпоративних клієнтів. Деталі в розділі 6.
- **Atlassian MCP (Rovo)** уже вміє віддавати changelog (`listJiraIssueChangelogs`), але по одній задачі. Добре для «Claude, чому задачі зависають у рев'ю?» на 20–50 задачах, погано для 5 000 задач. Це окремий канал, не заміна застосунку.

## 1. Які дані потрібні і де вони в Jira

| Що потрібно для process mining | Звідки в Jira | Ендпоінт |
|---|---|---|
| Список задач (кейсів) за фільтром | JQL | `POST /rest/api/3/search/jql` |
| Поля задачі: тип, пріоритет, проєкт, мітки, компоненти, створена, вирішена, поточний статус | `fields` | той самий пошук або `POST /rest/api/3/issue/bulkfetch` |
| Кожна зміна статусу з часом і автором | changelog, елементи з `field = "status"` | `POST /rest/api/3/changelog/bulkfetch` або `GET /rest/api/3/issue/{key}/changelog` |
| Зміни виконавця (для передач між людьми) | changelog, `field = "assignee"` | те саме |
| Категорія статусу (To Do / In Progress / Done) | довідник статусів | `GET /rest/api/3/status` або `/rest/api/3/statuses/search` |
| Спринти (для Scrum-аналітики) | поле Sprint і Agile API | `/rest/agile/1.0/board/{id}/sprint` |
| Погодження в Jira Service Management | approvals і SLA | `GET /rest/servicedeskapi/request/{id}/approval`, `/sla` |

### 1.1 JQL-пошук

- Старий `GET/POST /rest/api/3/search` замінений на **`/rest/api/3/search/jql`** ✅ (так званий enhanced search). Пагінація тільки через `nextPageToken`, без `startAt` і без загальної кількості `total`. Кількість окремо: `POST /rest/api/3/search/approximate-count`.
- Розмір сторінки до 100 задач із полями (більше, якщо просити тільки `id`) 🔸.
- `expand=changelog` у пошуку є, але історія в ньому може бути обрізана для довгих задач 🔸. Надійніше брати історію окремим запитом (нижче).
- Порада: в JQL завжди задавати межу часу, наприклад `project = ABC AND updated >= -180d ORDER BY created ASC`. Так і демо швидке, і лімітів менше.

### 1.2 Історія змін (changelog)

**Варіант A, пачкою:** `POST /rest/api/3/changelog/bulkfetch` ✅ (з'явився в грудні 2024, спочатку з позначкою Experimental; чи її зняли, треба перевірити 🔸).

```json
{ "issueIdsOrKeys": ["ABC-1", "ABC-2", "..."], "fieldIds": ["status", "assignee"], "maxResults": 1000 }
```

- Фільтр `fieldIds` дозволяє брати лише статус і виконавця, це суттєво зменшує відповідь 🔸 (за форумом до 10 полів і до 1 000 задач за виклик).
- Відповідь пагінована через `nextPageToken` 🔸.
- Є відомий баг про дублікати при пагінації (JRACLOUD-94906) 🔸. Отже треба дедуплікація за `history.id`.

**Варіант B, по одній задачі:** `GET /rest/api/3/issue/{key}/changelog?startAt=0&maxResults=100` ✅. Простий і стабільний, має підвищений ліміт швидкості (200 запитів/с). Для 1 000 задач це 1 000+ запитів: нормально для CLI, повільнувато для браузера (паралелити по 5–10).

Структура одного запису історії (спрощено):

```json
{
  "id": "10234",
  "created": "2026-10-03T09:15:22.000+0200",
  "author": { "accountId": "5b10...", "displayName": "Olena K." },
  "items": [
    { "field": "status", "fieldId": "status",
      "from": "10001", "fromString": "In Progress",
      "to": "10002", "toString": "Code Review" }
  ]
}
```

Важливо брати `from`/`to` (id статусу), а не лише назви: статуси перейменовують, а id лишається.

## 2. Авторизація: чотири шляхи

| Шлях | Як працює | З браузера напряму? | Для чого підходить |
|---|---|---|---|
| **API-токен** (email + токен, Basic auth) | користувач створює токен у профілі Atlassian | ❌ CORS на `*.atlassian.net` закритий ✅ | CLI, скрипт, локальна утиліта. Під бальні ліміти не потрапляє |
| **OAuth 2.0 (3LO)** | кнопка «Підключити Jira», користувач дає дозвіл, ми отримуємо токен | ✅ на `api.atlassian.com/ex/jira/{cloudId}/...` CORS дозволений. ❌ обмін коду на токен потребує `client_secret`, PKCE немає (ECO-283 «Gathering Interest») | **демо і веб-застосунок**, з крихітною функцією обміну токена |
| **Forge-додаток** | застосунок працює всередині Jira, UI в iframe, запити через `requestJira` від імені користувача | ✅ CORS взагалі не питання | платна версія на Marketplace: «дані не залишають Atlassian» (бейдж Runs on Atlassian) |
| **Розширення браузера** | розширення з дозволом на `*.atlassian.net` викликає REST, використовуючи вже відкриту сесію користувача | ✅ | приватність на 100%, працює і з Jira Data Center у корпоративній мережі |

Connect-додатки Atlassian згортає на користь Forge, тож для нового продукту Connect не розглядаємо.

### 2.1 Деталі OAuth 3LO ✅

- Реєстрація застосунку в Atlassian Developer Console, callback URL нашого сайту.
- Scope для читання: класичний `read:jira-work` (+ `read:jira-user` для імен) або гранулярні `read:issue:jira`, `read:issue.changelog:jira` 🔸, плюс `offline_access`, якщо потрібен refresh token.
- Обмін `code → access_token` на `https://auth.atlassian.com/oauth/token` вимагає `client_secret`. Implicit grant не підтримується.
- Після входу `GET https://api.atlassian.com/oauth/token/accessible-resources` повертає `cloudId` сайтів, до яких користувач має доступ.
- Refresh token ротується: кожне оновлення видає новий, старий вимикається.
- Щоб підключались чужі сайти (не лише наш), у консолі треба ввімкнути distribution і заповнити відомості про обробку персональних даних.

**Мінімальна серверна частина для демо:** одна функція (Cloudflare Worker або Vercel Function) `POST /token`, яка додає `client_secret` і пересилає обмін в Atlassian. Не має бази, не логує тіло, не бачить задач. Access token повертається в браузер і живе в пам'яті вкладки (не в localStorage). Це чесно вписується в обіцянку «ваші задачі не проходять через наш сервер».

### 2.2 Jira Data Center (Server)

- REST `/rest/api/2/search` зі старою пагінацією `startAt`/`maxResults` і `expand=changelog` (на DC історія в пошуку повна) 🔸.
- Окремого bulk changelog ендпоінта на DC **немає** 🔸. Тільки пошук з `expand=changelog` або по одній задачі.
- Авторизація: Personal Access Token (Bearer) або Basic. OAuth 2.0 провайдер є з версії 8.22.
- DC майже завжди у внутрішній мережі. Ні наш сайт, ні наша функція туди не дістануться. Реальні шляхи: розширення браузера, CLI, або експорт файлом.

## 3. Ліміти Jira Cloud ✅ (сторінка rate limiting оновлена 20.11.2026)

Три незалежні механізми:

1. **Бальна квота на годину** (з 2 березня 2026, тільки для Forge, Connect і OAuth 3LO застосунків). 1 бал за запит + 1 бал за кожну задачу у відповіді (користувачі й групи по 2). За замовчуванням **65 000 балів на годину, спільних для всіх сайтів, що використовують застосунок**. Після перевірки Atlassian можна отримати ліміт на кожен сайт: Free 65 000, Standard 100 000 + 10 × користувачі, Premium 130 000 + 20 × користувачі, максимум 500 000 на годину. Скидається щогодини за UTC.
2. **Burst-ліміт** на сайт, ендпоінт і метод: GET і POST 100 запитів/с, `GET .../changelog` 200/с. Діє і для API-токенів.
3. Ліміт записів на одну задачу (нас не стосується, ми лише читаємо).

При 429 приходять `Retry-After`, `X-RateLimit-Remaining`, `RateLimit-Reason`. Правило: поважати `Retry-After`, експоненційна пауза з випадковим розкидом.

**Оцінка вигрузки:**

| Обсяг | Запитів (пошук по 100 + bulk changelog по 1 000) | Балів (оцінка) 🔸 | Час із браузера |
|---|---|---|---|
| 500 задач | ~6 | ~1 000–2 000 | кілька секунд |
| 5 000 задач | ~55 | ~10 000–15 000 | до хвилини |
| 50 000 задач | ~550 | ~100 000+ | впирається в годинну квоту |

Висновок: демо на 1–5 тис. задач комфортне. Публічний сервіс з багатьма користувачами на OAuth вимагатиме заявки на tenant-квоту, або перенаправлення великих вигрузок у CLI з API-токеном.

## 4. Мапінг Jira → event log

Формат збігається з `xray-log` із concept.md (розділ 3.1).

| Поле event log | Значення з Jira | Примітка |
|---|---|---|
| `case_id` | `issue.id` (показуємо `issue.key`) | id не змінюється при переносі задачі в інший проєкт, key змінюється |
| `activity` | назва статусу, в який задача **увійшла** (`toString`), id в `to` | «подія = вхід у статус», тривалість статусу = до наступної події |
| `timestamp` | `history.created` | в UTC; часовий пояс сайту для звітів |
| `resource` | `history.author.displayName` (хто зробив перехід) | окремо зберігаємо `assignee_at_time`, відновлений з історії змін виконавця |
| атрибути кейсу | `issuetype`, `priority`, `project`, `labels`, `components`, `resolution`, `sprint`, `created`, `resolutiondate` | для фільтрів і порівнянь |
| атрибути події | `status_category` (To Do / In Progress / Done), `is_automation` | категорія з довідника статусів |

**Стартова подія.** Changelog не містить «створення у статусі X». Додаємо подію `Created` з часом `issue.created`, а початковий статус беремо з `fromString` першого переходу (або поточний статус, якщо переходів не було).

**Додаткові синтетичні події (опційно):** `Assigned to X` (зміна виконавця), `Sprint changed`, `Resolution set/cleared`, `Commented` (якщо колись захочемо «час до першої відповіді»).

Мінімальне перетворення (для ясності, не код продукту):

```js
for (const h of histories)
  for (const it of h.items)
    if (it.field === 'status')
      events.push({ case_id: issue.key, activity: it.toString,
                    timestamp: h.created, resource: h.author?.displayName ?? 'system' });
```

### 4.1 Підводні камені даних

- **Автоматизація.** Багато переходів робить Jira Automation або інтеграції (GitHub, CI). Автор `Automation for Jira` чи бот. Позначаємо `is_automation` і даємо фільтр, інакше «передачі між людьми» брешуть.
- **Масові операції і міграції workflow.** Bulk-переходи (100 задач закрили за хвилину) і зміна схеми workflow породжують неприродні події. Детектор: багато однакових переходів від одного автора в одну хвилину.
- **Перейменовані й видалені статуси.** Групувати за id, показувати актуальну назву з довідника.
- **Різні workflow у різних типів задач.** Bug і Story ходять різними шляхами; змішування дає «спагеті». Фільтр за типом задачі обов'язковий з першого дня.
- **Відкриті задачі.** Для них останній статус триває «досі». Рахувати окремо (WIP, вік задачі), не змішувати з тривалостями завершених.
- **Видалені користувачі і GDPR.** Ім'я може бути «Former user». Для показу іншим людям потрібна псевдонімізація (Людина A, B, C) одним перемикачем.
- **Календарний і робочий час.** Вихідні роздувають тривалості. Опція «робочі години» (Пн–Пт, 9–18, часовий пояс сайту) суттєво змінює картину.
- **Дублікати в bulk changelog** (див. 1.2): дедуплікація за `history.id`.

## 5. Яку аналітику це дає

Усе нижче рахується в браузері з event log, без додаткових запитів.

| Метрика | Як рахується | Що показує на демо |
|---|---|---|
| **Lead time** | від `Created` до першого входу в Done-категорію | «у середньому задача живе 11 днів» |
| **Cycle time** | від першого входу в In Progress-категорію до Done | «з них робота триває 4 дні, решта очікування» |
| **Час у кожному статусі** | сума інтервалів у статусі на кейс; середнє, медіана, P85 | таблиця і підсвітка на карті |
| **Час у погодженні / рев'ю / тестуванні** | те саме для статусів, які користувач позначив як «очікування» (Waiting for approval, Code Review, QA) | «погодження займає 38% часу задачі» |
| **Вузькі місця** | статуси з найбільшим сумарним і медіанним очікуванням; ріст черги в часі | червоні вузли на карті |
| **Повернення (rework loops)** | переходи назад по порядку статусів, повторні входи в той самий статус (QA → In Progress → QA) | «27% задач повертались з тестування хоча б раз» |
| **Варіанти процесу** | унікальні послідовності статусів, частоти | «80% задач ідуть 3 шляхами, ще 40 шляхів унікальні» |
| **Передачі між людьми (handoffs)** | зміни `assignee` у межах кейсу; граф «хто кому передає» | «задача в середньому міняє 3 виконавців» |
| **Flow efficiency** | час в активних статусах / lead time | одна цифра, яку розуміє будь-який менеджер |
| **Пропуски кроків** | задачі, що дійшли до Done без обов'язкового статусу (Review) | контроль відповідності процесу |
| **Throughput і WIP** | завершені за тиждень; кількість у роботі на дату | динаміка за місяці |
| **Порівняння зрізів** | усе вище за типом задачі, пріоритетом, командою, кварталом | «баги з High закриваються вдвічі швидше» |

Для Jira Service Management додатково: час до першої відповіді, порушення SLA, тривалість погоджень з `/servicedeskapi/.../approval`.

**Чого Jira не дасть:** реальної роботи поза статусами (людина взяла задачу, але статус не перевела), часу всередині статусу по етапах, справжніх зусиль (лише якщо команда веде worklog). Це варто чесно казати на демо.

## 6. Варіанти підключення для демо і рекомендація

| | A. OAuth + функція обміну токена | B. CLI з API-токеном | C. Розширення браузера | D. Forge-додаток | E. Через MCP / Claude |
|---|---|---|---|---|---|
| Як виглядає на показі | «Підключити Jira» → дозвіл → карта | запустити команду, кинути файл у браузер | встановити розширення, кнопка на сторінці Jira | встановити додаток у Jira | питаєш Claude словами |
| Чи бачимо ми дані | ні, лише обмін токена | ні | ні | ні (дані в Atlassian) | ні (дані йдуть у AI-клієнт користувача) |
| Data Center | ❌ | ✅ | ✅ | ❌ | ❌ |
| Великі обсяги | обмежує годинна квота застосунку | ✅ | ✅ | обмежує квота | ❌ по одній задачі |
| Зусилля | 2–3 дні (консоль, функція, потік входу) | 1–2 дні | 4–6 днів + публікація в Chrome Web Store | 1–2 тижні + рев'ю Marketplace | 0 днів |

**Рекомендація:**

1. **Для демо: варіант A.** Він найкраще продає ідею: живе підключення до Jira за пів хвилини. Серверна частина зводиться до однієї безстанової функції, що чесно зберігає обіцянку приватності. Це уточнення до concept.md, де на старт пропонувався CLI: з'ясувалось, що CORS на `api.atlassian.com` відкритий, тож кнопка в браузері реальна.
2. **Паралельно варіант B (CLI) з тим самим кодом конектора**, для великих вигрузок, Data Center і скептичних служб безпеки.
3. **Демо-дані без доступу до чужої Jira:** власний безкоштовний сайт Jira Cloud (до 10 користувачів) з згенерованими задачами та історією (скрипт створює 300–500 задач і проводить їх по статусах з реалістичними затримками). Змінити час подій API не дозволяє, тож або генерувати історію заздалегідь кілька днів, або для показу використовувати підготовлений файл event log, а живе підключення демонструвати на меншому наборі. Також є публічні Jira open source проєктів (Apache тощо) з анонімним доступом 🔸, але це Data Center, тож через CLI.
4. **MCP як окрема фішка, не основа.** Сценарій як у PM з МКІС: «Claude, скільки в середньому задачі чекають рев'ю в проєкті X за квартал?». Rovo MCP має `searchJiraIssuesUsingJql` і `listJiraIssueChangelogs` ✅, але `expand=changelog` у пошуку ігнорується (ECO-1614) ✅, тож Claude ходить по задачах по одній. Для 20–100 задач працює, для тисяч ні. Пізніше можна зробити власний MCP-сервер Process X-ray з інструментом `analyze_process(jql)`, який робить bulk-вигрузку і повертає готові метрики, а не сирі дані.
